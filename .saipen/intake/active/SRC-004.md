PROBLEM

BlipStatsRepository currently captures:

Clock.systemDefaultZone()

when the repository is created.

That Clock retains the timezone captured at creation.

Therefore, if the device timezone changes while the Problip process remains alive, these operations can continue using the OLD timezone:

* recordSuccessfulBlip()
* snapshot()
* PeriodKeys day calculation
* PeriodKeys week calculation
* PeriodKeys month calculation

This can persist a successful blip under the wrong local TODAY/WEEK/MONTH bucket.

The visible statistics surfaces have a second part of the same defect.

SettingsScreen and MainStatsStrip currently schedule a delay to the next midnight using ZoneId.systemDefault(), but the delay is calculated before a timezone/time change and there is no explicit invalidation for:

* Intent.ACTION_TIMEZONE_CHANGED
* Intent.ACTION_TIME_CHANGED
* Intent.ACTION_DATE_CHANGED

Changing the timezone or wall clock while either screen remains composed can therefore leave:

* repository calendar authority stale
* displayed statistics stale
* the scheduled next-midnight wake aimed at the wrong boundary

TARGET BEHAVIOUR

The current device timezone must be authoritative without recreating:

* the Application
* BlipStatsRepository
* ProblipViewModel
* Activity
* foreground service
* scheduler

A timezone change must affect the next statistics calculation immediately.

A wall-clock/date/timezone change must cause visible statistics to recompute and the next midnight wake to be recalculated.

PART 1 — REMOVE CAPTURED PRODUCTION TIMEZONE

Do not retain Clock.systemDefaultZone() as the production calendar-zone authority.

Introduce one small testable calendar authority abstraction.

Keep it narrow.

A suitable design is conceptually:

current instant source
+
current zone source
->
current LocalDate / PeriodKeys

Production must resolve ZoneId.systemDefault() dynamically when current period keys are requested.

Tests must still be able to inject deterministic time and zone behaviour.

Do not create a general time framework.

Do not add a dependency.

Acceptable implementation shapes include:

* a small PeriodKeysProvider
* a small CalendarAuthority
* injected instantProvider + zoneProvider functions

Choose the smallest design that keeps tests clean.

IMPORTANT

A fixed Clock remains acceptable inside tests.

A captured system-default Clock is NOT acceptable as production authority.

Both:

snapshot()

and:

recordSuccessfulBlip()

must use the same current calendar-authority contract.

PART 2 — PRESERVE PERIOD LOGIC

Do not change the meaning of:

* TODAY
* ISO WEEK
* MONTH
* TOTAL
* earned Premium

PeriodKeys remains the sole period-key logic.

Do not migrate stored records.

When the device timezone changes, an existing persisted bucket from the previous local calendar simply behaves like any other old period:

* snapshot returns zero for a no-longer-current period
* the first successful blip under the new period starts that period at 1
* TOTAL remains unchanged except for the new blip
* earnedPremium remains irreversible

Do not attempt to redistribute historical blips between timezones.

The app does not store timestamps and cannot reconstruct history.

* ACTION_DATE_CHANGED

* ACTION_TIMEZONE_CHANGED

The receiver/listener must exist only while the relevant composed UI is alive.

Do not add:

* WorkManager

* polling

A suitable shape is a shared:

It should:

2. schedule the next local midnight using the CURRENT ZoneId.systemDefault()
3. bump/restart when a relevant system time/date/timezone broadcast arrives
4. recalculate the next midnight after every invalidation
5. unregister cleanly when composition leaves

Use the existing Android/AndroidX API level contracts already available to the project.
